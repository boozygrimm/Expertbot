# Анализ проекта ExpertBot

## Обзор

Telegram бот для игры "Алхимия" с системой экспедиций, рейдов, крафта и управления бойцами.

## Структура проекта

### Основные модули

- `handlers/alc_*.py` — игровая логика (экспедиции, рейды, крафт, бойцы)
- `handlers/social_rp.py` — социальное ролевое
- `ai_logic.py` — интеграция с AI API
- `database.py` — работа с MongoDB
- `config.py` — конфигурация

### Размеры модулей

- `alc_expeditions.py` — > 25000 токенов (слишком большой)
- `alc_raids.py` — большой
- `alc_base.py` — большой
- `alc_core.py` — большой

## Проблемы

### 1. Архитектурные

- **Большие модули** — некоторые файлы слишком большие (> 25000 токенов)
- **Глобальные переменные** — состояние в памяти, теряется при рестарте
- **Дублирование кода** — одинаковые функции в разных модулях
- **Циклические импорты** — потенциальная проблема (прямо сейчас нет)

### 2. Качество кода

- **Широкие исключения** — много `except Exception:` без конкретизации
- **Частое использование `.get()`** — 1552 occurrences, может быть неочевидно
- **Много глобальных переменных** — 92 occurrences

### 3. Тестирование

- **Покрытие тестами** — хорошее для критической логики
- **Отсутствие тестов** — для UI функций и callback handlers

## Плюсы

- ✅ Нет `TODO/FIXME/XXX/HACK` комментариев
- ✅ Нет пустых `pass` блоков
- ✅ Используются type hints
- ✅ Структура модульная
- ✅ Используются async/await для IO операций
- ✅ Хорошее покрытие тестами для критической логики

## Планы по улучшению

### Приоритет 1: Критические улучшения

#### 1.1 Разбить большие модули

**Проблема:** `alc_expeditions.py` > 25000 токенов

**Решение:**
```
handlers/alc_expeditions/
├── __init__.py
├── models.py          # модели данных (Expedition, Event)
├── logic.py           # бизнес-логика (process, finalize)
├── handlers.py        # callback handlers
├── utils.py           # утилитные функции
└── constants.py       # константы
```

**Выгода:** легче поддерживать, меньше конфликтов при мерджах

#### 1.2 Вынести глобальные переменные

**Проблема:** состояние в памяти теряется при рестарте

**Решение:**
- Использовать Redis для сессий
- Хранить черновики в БД
- Кэшировать редко меняющиеся данные

**Выгода:** персистентность, масштабируемость

#### 1.3 Устранить дублирование

**Проблема:** одинаковые функции в разных модулях

**Решение:**
- Создать `handlers/alc_common.py` для общих функций
- Вынести `get_element_name`, `get_element_emoji`, `shorten_button_text`
- Объединить похожие функции

**Выгода:** меньше кода, легче поддерживать

### Приоритет 2: Улучшение качества кода

#### 2.1 Конкретизировать исключения

**Проблема:** много `except Exception:`

**Решение:**
```python
# Вместо:
try:
    ...
except Exception:
    ...

# Использовать:
try:
    ...
except (TelegramBadRequest, ValueError) as e:
    ...
```

**Выгода:** легче отладка, меньше скрытых ошибок

#### 2.2 Уменьшить использование `.get()`

**Проблема:** 1552 occurrences, может быть неочевидно

**Решение:**
- Использовать `dict.get()` с явным дефолтом

**Выгода:** более явный код, меньше ошибок

## Последние изменения (зависимости и Social RP, ноябрь 2026)

- `pymorphy2` → `pymorphy3` в `requirements.txt`. Причина: pymorphy2 0.9.1 на
  Python 3.11+ падает с `AttributeError` (внутри удалённый `inspect.getargspec`),
  а `except` в `handlers/social_rp.py` ловил только `ImportError` — модуль не
  импортировался, и бот не стартовал в собственном Docker-образе (`python:3.12-slim`).
  Теперь импорт пробует `pymorphy3`, затем `pymorphy2`, и любое исключение ведёт
  к запланированному fallback на упрощённое склонение.
- Починено склонение ников: `safe_decline_name` передавал в pymorphy грамеммы
  `ins`/`dat`/`acc`/`abl`, которых не существует (нативные имена — `ablt`/`datv`/
  `accs`/`loct`), pymorphy бросал `ValueError`, и единственный вызов
  (`generate_local_fallback`, творительный падеж) молча возвращал ник без склонения.
  Добавлена карта `CASE_GRAMMEMES` (принимает и старые сокращения, и нативные имена)
  и сохранение регистра ника, так как pymorphy отдаёт форму в lowercase.
- Тестовый контур: `tests/test_social_rp.py` больше не подменяет `sys.modules`
  на `MagicMock` (это ломало соседние тесты при запуске всего набора), добавлены
  тесты склонения ников и сквозные тесты RP-сообщения.

### Исправление грамматики RP-сообщений

Как только склонение заработало, стали видны ошибки выбора падежа и рода —
до этого они были замаскированы тем, что ник и глагол просто не менялись.

| Было | Стало | Причина |
| --- | --- | --- |
| Маша обняла Иван**ом** крепко. | Маша обняла Иван**а** крепко. | падеж цели был захардкожен как творительный для всех действий, хотя переходные глаголы требуют винительного |
| Вася дал пять Нат**ой**. | Вася дал пять Нат**е**. | «дать пять» и «пожать руку» требуют дательного |
| Маша **дал** пять Ивану. | Маша **дала** пять Ивану. | pymorphy разбирает «дал пять» как существительное, женская форма не образовывалась |
| Маша **сделал клась** Ивана. | Маша **сделала кусь Ивану**. | `inflect({'femn'})` для «сделал кусь» даёт мусор; падеж — дательный, как в мемном обороте «сделать кусь кому» |
| Маша **раздел** Ивана. | Маша **раздела** Ивана. | омоформа: `parse()[0]` для «раздел» — существительное «раздел» |
| Маша **сделал** что-то с Иваном. | Маша **сделала** что-то с Иваном. | fallback-фраза не имела женской формы |

Решение: падеж цели выбирается по действию (`ACTION_CASES`, `DEFAULT_ACTION_CASE`,
`UNKNOWN_ACTION_CASE`; дательный задан для «пожать руку», «дать пять» и «кусь»),
женские формы для известного набора действий заданы явной
картой `FEMININE_VERB_FORMS` и применяются раньше морфологии, а морфологический
путь (`_feminine_via_morph`) разбирает только первое слово фразы, ищет разбор с
`VERB+past+masc` (а не `parse()[0]`) и отбрасывает результат, не оканчивающийся
на «-а». Глаголы действий вынесены в `ACTION_VERBS`, поэтому тест проверяет, что
у каждого действия есть женская форма и валидный падеж.
- Итог: `unittest discover -s tests` — 126 OK, `pytest tests` — 162 passed
  (до правок: 7 failures / 2 errors и падение collection у pytest).

## Последние изменения (отключение системных уведомлений, ноябрь 2026)

Игрок получает от алхимии фоновые DM-сообщения, которые он не запрашивал:
утренний отчёт и отчёты о нападениях на форт. Обе категории теперь можно
отключить кнопкой в самом сообщении и включить обратно в главном меню базы.

### Общий модуль настроек `handlers/alc_notifications.py`

Флаги, тексты кнопок, клавиатуры отчётов и кнопки-переключатели собраны в одном
модуле, который **не импортирует другие хендлеры**: его подключают сразу три
контура — `alc_base` (меню базы), `alc_tasks` (утренний отчёт) и `alc_raids`
(отчёты о нападениях). Любая зависимость от них создала бы цикл импортов.

Каждая категория — отдельное булево поле в документе игрока
(`db.alchemy_players`):

| Категория | Поле | Что глушит | Что остаётся |
| --- | --- | --- | --- |
| Утренний отчёт | `morning_report_muted` | «📊 УТРЕННИЙ ОТЧЕТ» (`process_barracks_upkeep`, cron 3:10 МСК) | — |
| Нападения на форт | `raid_report_muted` | «🛡 АТАКА НА ФОРТ» (рейд другого игрока), «🛡 НАЛЁТ НА ФОРТ» (случайная NPC-банда) | «☠️ ОТЧЁТ О РЕЙДЕ» — итоги собственного рейда игрока |

Отсутствие поля трактуется как «уведомления включены», поэтому миграция
существующим профилям не нужна; `get_or_create_player` дописывает недостающие
ключи шаблона и сохраняет их точечно через `$set`, произвольные поля не
затираются.

Итоги собственного рейда намеренно не гейтятся: это отклик на действие игрока,
а не фоновая рассылка, поэтому в таком сообщении нет и кнопки отключения (иначе
она обещала бы то, чего не делает).

### Кнопки

- В сообщении отчёта — «🔕 Не присылать отчёты» / «🔕 Не присылать отчёты о
  нападениях» рядом над «❌ Закрыть». После нажатия флаг записывается, а кнопка
  отключения убирается из этого же сообщения (`edit_reply_markup`), чтобы её
  нельзя было нажать повторно; игрок получает алерт с подсказкой, где включить
  обратно. Ошибка правки клавиатуры логируется и не роняет хендлер.
- В сервисном ряду главного меню базы — два независимых переключателя:
  «📊 Отчёты: вкл / 🔕 Отчёты: выкл» и «⚔️ Нападения: вкл / 🔕 Нападения: выкл».
  Подпись кнопки всегда показывает текущее состояние, меню перерисовывается
  через `get_base_content` + `safe_edit_text`.

### Хендлеры

| Callback | Хендлер | Модуль |
| --- | --- | --- |
| `alc:report_mute` | `mute_morning_reports` | `alc_base.py` |
| `alc:report_toggle` | `toggle_morning_reports` | `alc_base.py` |
| `alc:raid_report_mute` | `mute_raid_reports` | `alc_raids.py` |
| `alc:raid_report_toggle` | `toggle_raid_reports` | `alc_base.py` |

Mute-хендлер утреннего отчёта живёт в `alc_base.py`, потому что у
`alc_tasks.py` нет своего `router` (модуль подключён только к планировщику);
mute-хендлер нападений — в `alc_raids.py` рядом с `close_pm_report`, у которого
свой роутер уже зарегистрирован. Toggle-хендлеры обоих категорий — в
`alc_base.py`, так как они перерисовывают меню базы. Общая механика
переключателя вынесена в `_toggle_mute_setting`, чтобы не дублировать чтение
профиля, запись флага и перерисовку меню для каждой категории.

### Экономика не зависит от уведомлений

Флаги гейтят **только отправку сообщения**. Списание энергии за бойцов,
начисления наследия и миров, запись `barracks_report`, потери добычи при налёте,
пленные, сработавшие ловушки и `action_counters` выполняются всегда. Отключение
уведомлений не даёт игроку преимущества и не наказывает его.

Решения об отправке вынесены в чистые функции `should_send_morning_report`
(`alc_tasks.py`) и `should_send_raid_defense_report` (`alc_notifications.py`),
чтобы их можно было тестировать без планировщика, рейдов и БД.

Отдельная чатовая фича `daily_reports` (`handlers/admin_cron.py`, `db.settings`,
`{setting: "daily_report", chat_id, is_active}`) — это сводка по чату для
админов, и с per-player флагами алхимии она не связана.

- Итог: `unittest discover -s tests` — 155 OK, `pytest tests` — 200 passed
  (до утреннего отчёта: 126 OK / 171 passed; после утреннего отчёта: 138 / 183).
