## 2. HTTPS и хостинг: конкретное решение

**Домена покупать не нужно, если API живёт в процессе бота на Render.** У
веб-сервиса Render есть HTTPS-адрес `https://<имя-сервиса>.onrender.com`, и
Mini App по требованиям Telegram открывается только по HTTPS — это условие
выполняется без покупки домена.

Тогда два варианта, и они оба рабочие:

1. **Всё в боте (проще, рекомендуется для первой версии).** Статика лежит в том
   же `aiohttp`-процессе: `GET /miniapp/` отдаёт страницу, `POST /api/craft`
   работает на том же origin. CORS не нужен вообще, CSP остаётся
   `connect-src 'self'` — как сейчас в `miniapp_backend/telegram_stand.py`.
2. **Статика отдельно (как выбрал владелец).** Страницы на Cloudflare Pages или
   GitHub Pages, API на Render. Тогда обязательно: точный источник в CORS
   (не `*`), `connect-src` с адресом Render в CSP, и проверка, что бесплатный
   хостинг не переписывает заголовки.

Разница не в деньгах, а в количестве мест, где можно ошибиться. При 10–30
игроках трафик статики ничтожен: по `FREE_CAPACITY_OPTIONS.md` текущий черновик
— около 0,76 МБ на холодную загрузку, то есть 1000 загрузок ≈ 0,76 ГБ, что
далеко от лимитов Render Hobby (5 ГБ/мес на workspace).

**Рекомендация:** начать с варианта 1 (один origin), а вынести статику на
бесплатный хостинг только если упрёмся в исходящий трафик Render. Это не
противоречит выбору владельца, а откладывает лишнюю работу до появления
причины. Решение за владельцем — см. вопрос 1 в конце.

## 3. Доступ по группам: что именно проверять

Сейчас `AuthMiddleware` (`handlers/auth.py:12–38`) пропускает **все личные
сообщения** без проверки и ограничивает только группы через коллекцию
`auth_chats` со `status: "approved"`. Для Mini App это не годится напрямую:
`initData` даёт Telegram user ID, а не чат.

Два способа связать игрока с одобренной группой, оба опираются на фактические
данные:

1. **По участникам одобренных групп** — нужен вызов `getChatMember` для каждой
   одобренной группы (`auth_chats`), то есть N запросов на вход игрока. При
   10–30 игроках и единичных группах это приемлемо, но результат надо кешировать.
2. **По известным игрокам** — игрок уже есть в `alchemy_players` и играл через
   бота, значит он «свой». Это дешевле и не требует Telegram-запросов, но не
   отличает нового участника группы от постороннего.

Чего делать нельзя: пускать любого, кто открыл ссылку (владелец выбрал
противоположное), и нельзя вычислять доступ из параметра URL или `chat_id` с
клиента.

**Открытый вопрос:** какой из двух способов. Нужен ответ владельца.

## 4. Крафт со списанием: что это требует

Главный риск проекта. Факты из кода:

- `handlers/alc_lab.py:411–437` — читает профиль целиком, списывает ингредиенты
  в памяти, пишет обратно **весь** `inventory` через `$set`. В фильтре только
  `user_id`; версии документа и проверки остатка в самой записи нет.
- `handlers/alc_tasks.py:188–191` — то же с `inventory` и `production_slots`,
  ежечасно.
- `process_expeditions_tick` — каждую минуту (инвентарь не пишет, но конкурирует
  за документ).
- `active_mixes` живёт в памяти процесса: рестарт бота стирает собранный котёл.

Отсюда минимум для первой версии:

1. **Один слой записи.** Условная запись по версии документа, повтор при
   конфликте, ключ идемпотентности на операцию. Через него проходят и
   `lab_mix` в боте, и крафт в Mini App.
2. **Три писателя переводятся в первую очередь:** `alc_lab` (крафт),
   `alc_tasks` (производство), `alc_expeditions` (тик). Пока хоть один пишет
   `$set` всего инвентаря, гарантии нет — всего таких мест 27 в 10 файлах
   (`alc_achievements`, `alc_base`, `alc_build`, `alc_core`, `alc_crucible`,
   `alc_intro`, `alc_production`, `alc_quests`, `alc_raids`, `alc_tasks`).
3. **Проверка на копии базы**, а не на глаз: два параллельных крафта, крафт +
   производство, повтор запроса, рестарт между чтением и записью.

Это единственная часть, где ошибка необратима для игрока. Её можно полностью
сделать и проверить, не выпуская ни одного экрана Mini App.

## 5. Объём первой версии: только лаборатория

| Экран | Готово | Нужно |
|---|---|---|
| Парк (вход) | концепт `design/bender_lunapark_concept.png` | одна страница с входом в лабораторию |
| Лаборатория: склад, рецепты, котёл | `miniapp_preview/` (сейчас на `offline_adapter.js`) | переключить на API |
| Профиль | `miniapp_backend/profile.py` | отдавать только склад и открытые элементы |

База, производство, задания, экспедиции, рейды — вне первой версии. Это
согласуется с `ALCHEMY_MINI_APP_PLAN.md`, где следующий шаг после крафта —
«следующие механики по одной».

## 6. Порядок работ

1. **Слой записи + перевод трёх писателей** (без интерфейса, проверка на копии
   базы). Самая рискованная часть, делается первой.
2. **API:** `GET /api/profile`, `POST /api/craft` поверх слоя записи; `initData`
   уже проверяется в `miniapp_backend/auth.py`.
3. **Интерфейс:** `miniapp_preview/` на API вместо офлайн-адаптера.
4. **Стенд:** тестовый бот + изолированная база, доступ по группам.
5. **Пилот:** 2–3 игрока, затем остальные из одобренных групп.

## 7. Ворота готовности

- нет потери или задвоения при одновременных действиях бота и Mini App;
- инвентарь после крафта в Mini App совпадает с тем, что видит бот;
- повтор одного запроса не списывает второй раз;
- рестарт бота не ломает открытый Mini App молча;
- команды бота работают как раньше;
- посторонний без одобренной группы получает отказ, а не склад.

## 8. Что нужно от владельца

1. **Хостинг:** начать с одного origin (всё в боте) или сразу разносить
   статику? Рекомендация — начать с одного.
2. **Доступ:** по участникам одобренных групп (N запросов `getChatMember`) или
   по известным игрокам из `alchemy_players`?
3. **Тестовый контур:** готов ли отдельный тестовый бот и отдельная база, или
   проверяем на копии рабочей?
4. **Крафт в боте:** можно ли поправить `lab_mix` (перевести на слой записи),
   сохранив поведение команды? Без этого слоя запись из Mini App небезопасна.
