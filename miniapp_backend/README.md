# Серверный фундамент Mini App — изолированная разработка

Это **не включено в боте и не развёрнуто**. Есть два принципиально разных стенда:

- `python -m miniapp_backend.sandbox` — публичный фальшивый токен, общий
  искусственный профиль, пробный крафт и производство только в памяти.
  В производстве можно разобрать станцию, запустить новую с ручным трудом или
  духом и вручную прогнать один тестовый час. Добыча сразу попадает на склад;
  часы не идут автоматически. После 24 тестовых часов линия останавливается,
  дух не возвращается; при досрочном демонтаже возвращается, энергия — нет.
  Фальшивые маршруты `/api/dev/*` существуют исключительно в этой песочнице.
  Профиль общий для всех открывших её, сбрасывается при рестарте.
- `miniapp_backend.telegram_stand` — отдельный **только read-only** стенд с
  Telegram SDK, проверкой Telegram initData, allowlist и чтением из *отдельной
  тестовой* MongoDB. Он не подключён к боту и сам по себе не запускается.
  Тестовый крафт туда не перенесён. Настоящий Telegram и настоящая Mongo ещё
  не проверялись: автоматические тесты используют имитации.

В `crafting.py` вынесен чистый расчёт одного крафта по имеющимся рецептам;
песочница применяет его только к искусственному профилю. Функция не пишет в
Mongo и пока не используется существующим ботом. Она не обеспечивает атомарную
запись, согласование конкурентных писателей и идемпотентность после рестарта;
подключать её к рабочим данным до решения этих задач нельзя. Отдельный
`isolated_store.py` пробует условную запись и журнал операций только на
изолированной тестовой БД; ограничение в 256 ключей блокирует последующие
действия вместо удаления старых ключей и не является production-решением.
Автотесты с mock DB не проверяют большинство гарантий и режимов настоящего
MongoDB. Дополнительно изолированный прототип сопоставляет расчёт производства
с текущим Python-планировщиком при мокированных I/O и проверяет совместные
операции с крафтом. Рабочий планировщик не изменён и не подключён; сохранение
идентификаторов запусков и реальная Mongo ещё не проверены. Песочница использует
внедряемый расчёт производства и копии таблиц, чтобы не импортировать модули,
инициализирующие настоящий клиент Mongo. Для неё миры и их бонусы не заданы;
копии таблиц производства больше не с чем сверять: текстовые обработчики
алхимии из бота удалены, эталон остался только здесь. Условия перехода —
в `GAMEPLAY_SAFETY.md`.

Текстовой алхимии в боте больше нет: `handlers/alc_*` (кроме
`handlers/alc_recipes.py` с данными рецептов) удалены, вместе с ними удалён
адаптер `production.py`, который брал правила у старых обработчиков. Расчёт
производства живёт в `production_engine.py` с внедряемыми параметрами, песочница
передаёт свои таблицы. Сверочные тесты с ботом (`production_characterization`,
`sandbox_production_parity`, `alchemy_parity`) удалены, потому что сверять стало
не с чем.

## Как устроен Telegram-стенд

Клиент получает `Telegram.WebApp.initData`, отправляет его только в теле POST
`/api/session`. Сервер проверяет HMAC, срок и Telegram user ID; проверяет
allowlist и выдаёт случайный короткоживущий bearer-токен. `/api/alchemy/me`
читает профиль только по идентификатору из серверной сессии и отдаёт ограниченные
поля; клиент не выбирает user ID. Клиент держит токен только в памяти, не в URL,
хранилище браузера или логах. `DELETE /api/session` закрывает сессию. Ошибки и
профили помечены `Cache-Control: no-store`, CORS не включён; есть CSP.

Подписанные входные данные одноразовы **в рамках одного процесса**; повтор с
другим порядком/кодировкой параметров отсекается. Сессия действует 10 минут,
входные данные принимаются не старше 15 минут; после ошибки, неизвестного
результата обмена или истечения сессии нужно заново открыть Mini App. Это
намеренное ограничение тестового этапа. Сессии и история повторов в памяти:
после рестарта исчезают; между процессами не разделяются. Нет надёжной защиты
повторов при рестарте или масштабировании. Сам факт подписи не предотвращает
кражу ещё не использованного initData. Лимиты запросов и сессии в постоянном
хранилище, мониторинг и полноценная проверка безопасности — обязательны до
выхода за пределы изолированного теста.

## Запуск только после отдельного согласования

Нужны **отдельный тестовый бот**, **изолированная тестовая MongoDB** с
синтетическими/обезличенными данными и учётной записью только на чтение
`alchemy_players`, публичный HTTPS-прокси и добавление URL Mini App в тестовом
боте. Имена переменных среды: `LUNAPARK_TEST_BOT_TOKEN`,
`LUNAPARK_TEST_MONGO_URI`, `LUNAPARK_TEST_DB`, `LUNAPARK_TEST_USERS` (список
положительных Telegram ID через запятую) и подтверждение
`LUNAPARK_STAND_CONFIRM=isolated_test_only`. Сервер допускает только имя базы
`lunapark_test_*`; эта проверка **не доказывает**, что кластер и учётные данные
изолированы. Не использовать токен рабочего бота, production URI или реальные
профили. Не отправлять секреты в чат и не записывать их в репозиторий/логи.

Команда `python -m miniapp_backend.telegram_stand --port 8002` слушает localhost
по умолчанию и обслуживает HTTP, не TLS. Для внешнего доступа нужен отдельно
настроенный HTTPS-прокси с ограничениями запросов и безопасными логами. Не
экспонировать этот процесс напрямую и не считать его production-ready. Даже
после локальных тестов запуск стенда и настройка тестового бота/сервисов
требуют решения владельца: могут расходовать ресурсы и квоты.

## Локальные проверки без доступа к реальным сервисам

```sh
python -m pip install aiohttp motor mongomock-motor aiogram python-dotenv Pillow apscheduler==3.10.4
python -m unittest -v tests.test_miniapp_backend tests.test_miniapp_sessions tests.test_lunapark_sandbox tests.test_miniapp_crafting tests.test_miniapp_isolated_store tests.test_sandbox_production
npm ci --prefix miniapp_preview
MINIAPP_PYTHON="$(command -v python)" npm test --prefix miniapp_preview
```

Node-тесты используют jsdom, подменённый SDK и локальные серверы с фальшивой
подписью; Mongo-тест использует `mongomock-motor`. Они проверяют путь
интерфейс → вход → профиль, но не реальный Telegram WebView, сетевой TLS,
Render или работу настоящего кластера MongoDB.
