# Первая изолированная проба новости

`live_trial.py` — альтернативный поэтапный ручной запускатель одной новости,
не устанавливающий сервисы, не включающий сбор лент и не публикующий в каналы
или группы. Локальные тесты подменяют внешние службы.

Одна живая проба: пользователь подготовил на InstaBox публичный пост
`https://t.me/durov/552` и исправил сценарий, сохранив оригинал отдельно. Затем
через личку бота поставил исправленный сценарий в общую очередь и подтвердил,
что видео пришло. До этого он подтвердил и обычный кружок после обновления
воркера. Эта отдельная проба не доказывает качество будущих сценариев.

Отзывы по содержанию: модель сначала добавила неподтверждённое утверждение,
а после ручной правки итоговый сюжет и строка сделали главным принимаемый код
и видео, упустив основное изменение: Telegram Designers перестали принимать
статичные макеты, видео без кода и текстовые концепции. Владелец также попросил
больше и острее юмора, например подкол о программистах у Пашки. Шутливые
догадки нельзя выдавать за сведения источника. Совпадение цитат с источником
не гарантирует ни смысл всей реплики, ни правильный выбор главной новости;
ручная проверка остаётся нужна.

Для продолжения подготовлен альтернативный маршрут через бота: одно сообщение
в личке владельца с готовым сценарием поступает в отдельную Mongo-коллекцию на
стороне бота и отправляется в ту же аренду и общий слот воркера, что и кружки.
Таким образом, переносить Mongo URI на InstaBox не требуется. Публикации в
канал и пересылки в группы нет; готовый MP4 автоматически отправляется только
владельцу на проверку. Повтор того же сценария не создаёт второго задания, а
другой сценарий не займёт уже использованный пробный слот. Слот не очищается
автоматически. После подтверждённой доставки `review_sent` и сохранения ID
сообщения владелец может вручную открыть его для следующего сюжета командой
`/news_trial_next <UUID>` из `/news_trial_status`. Прошлые карточка и задача
остаются сохранены; та же версия не отправляется повторно. Старая команда с
UUID предыдущего сюжета не открывает слот нового. При неопределённой отправке,
ошибке или незавершённом рендере команда откажет: сначала нужен ручной разбор.

Для обследованной установки InstaBox подготовлен узкоспециализированный
`video_prototype/deploy_news_trial.py`: `--check` только проверяет текущую
конфигурацию, подготовленный код, резерв и health; запуск без параметров
перезапускает службу и может прервать обычное медиа. При ошибке он пытается
восстановить прежние настройки и подтвердить health; это не гарантия успешного
отката. Скрипт жёстко привязан к конкретным путям и хешам, не является
универсальным установщиком. Его локальные тесты подменяют systemd и health.

Этот маршрут выключен по умолчанию в коде. При последней подтверждённой
живой пробе на Render был включён `NEWS_OWNER_TRIAL_ENABLED=1`, а на воркере —
`NEWS_WORKER_ENABLED=1`; перед дальнейшими действиями необходимо проверить
актуальное состояние. Остальные новостные флаги бота должны оставаться
выключенными, иначе пробный маршрут не включится. Автоматические ленты и
Gemini-редактор при приёме готового сценария не запускаются, но озвучка на
воркере использует квоту Gemini. Любые последующие обновления и перезапуски
нужно согласовывать: перезапуск активного воркера может прервать текущий кружок.
Пробный слот после первой доставки занят и автоматически не очищается. Команда
для открытия следующего слота в текущих изменениях ещё требует отдельного
обновления бота; нельзя считать её работающей на Render до такого обновления.

После согласованной установки проверенный текст отправляется владельцем в
личке бота одной командой `/news_trial` с полями `Источник:`, `Строка:` и
отдельными строками `Бендер:` / `Киберсенсей:`. `/news_trial_status` показывает
состояние; при неопределённом результате не повторять вслепую. Локальная папка
сценария на InstaBox остаётся без изменений. Срок рендера не зафиксирован,
а обычная задача, пришедшая после начала новостного рендера, будет ждать.

## Альтернативный путь через ручной CLI

Далее описан первоначальный ручной путь `live_trial.py`: он требует доступ к
общей Mongo непосредственно с машины запуска. Для описанного выше маршрута
через бота перенос Mongo URI на InstaBox не нужен.

### Что нужно проверить до запуска CLI

- Отдельно согласовать передачу и установку изменений. На **существующем**
  видеоворкере должна работать совместимая версия с `NEWS_WORKER_ENABLED=1`.
  Такая версия была установлена для пробы; актуальное состояние надо проверить.
  Не запускать второй воркер с независимым слотом: он может конкурировать с
  действующей студией и обойти защиту очереди.
- Запускатель должен видеть именно ту MongoDB, которую использует рабочий бот:
  `beleyakov_db.bender_video_queue`, и именно тот защищённый воркер, которым
  он пользуется. Потребуются существующие настройки `MONGO_URI`,
  `BENDER_WORKER_URL`, `BENDER_WORKER_KEY` (или локальный `VIDEO_WORKER_KEY`).
  Не копировать значения в чат, командную строку или логи. Наличие документа
  очереди и capability не доказывает, что выбрана **правильная** база/служба:
  их соответствие нужно подтвердить на месте. Нельзя использовать отдельную
  тестовую очередь вместо общей: тогда приоритет обычных задач не сохранится.
- Проверить доступ к одной публичной HTTPS-новости или публичному Telegram-посту,
  имеющиеся ключи Gemini и их квоты, диск, зависимости и FFmpeg. Редактор
  использует ключ из `GEMINI_KEYS`/`GEMINI_API_KEYS`/`GEMINI_API_KEY`, иначе
  существующие ключи проб InstaBox. Текстовая модель — `GEMINI_CHAT_MODEL` из
  проекта. Не подключается новый сервис; реальные запросы расходуют квоту.
- При проверке доставки нужен корректный существующий `ADMIN_ID` в окружении
  и токен **того же бота** (`TELEGRAM_TOKEN`, `BOT_TOKEN` или локальный файл
  `/data/video-prototype/.env`). Отправка возможна только этому ID; проверить
  настройки на месте, не раскрывая их. Это не тестовая группа. Владелец должен
  иметь возможность получать личные сообщения бота. Команда доставки не
  запускает второй polling.
- Для исключения случайного запуска команд, затрагивающих MongoDB, требуется
  после проверки явно задать `NEWS_TRIAL_SHARED_QUEUE_CONFIRMED=1` в окружении.
  Это не проверка правильности подключения и не разрешение на развёртывание.

Тестовая карточка и задачи записываются в отдельные коллекции с UUID пробы;
сам список обычных задач не меняется. При каждом шаге запуска временно берётся
существующая общая аренда очереди, обычные задачи проверяются первыми, затем
задание выполняется в общем слоте воркера. Если обычный запрос поступит уже
после старта рендера новости, он будет ждать: текущий рендер не прерывается.
После прерванного рендера воркер может блокировать новые задания до ручного
разбора. Состояния на диске и в БД не очищаются автоматически.

### Команды CLI после подготовки среды

Примеры запускаются из корня установленной копии проекта подходящим Python;
`ПУТЬ_ПРОБЫ` — новая папка вне Git, её родитель должен существовать. Значения
и секреты ниже не нужно присылать в чат. Директория создаётся с правами 0700,
JSON — 0600. Содержимое новости, сценарий и цитаты сохраняются локально.

1. После ручного подтверждения общей очереди и защищённого адреса воркера:

   ```bash
   python -m news_prototype.live_trial check
   ```

   `ready` означает лишь, что документ очереди существует и воркер объявил
   `news-story-v1`. Доступность Gemini/TTS, диска, Telegram и правильность
   выбора служб команда не доказывает. Рабочие news-флаги бота не требуются.
2. Одна новость, один вызов редактора, без рендера и отправки:

   ```bash
   python -m news_prototype.live_trial prepare --folder ПУТЬ_ПРОБЫ \
     --url 'https://t.me/имя_канала/123' --accent 'Нужный акцент'
   ```

   Допускается обычная открытая HTTPS-статья. `--text-file ПУТЬ` позволяет
   подать сохранённый локальный текст, если саму страницу нельзя прочитать.
   В `source.json` записан использованный материал; в `prepared.json` —
   сценарий и цитаты. `needs_source` означает, что материала недостаточно,
   `skipped` — редактор отказался, `editor_failed` — результат не подтверждён.
   Такую папку повторно запускать нельзя: перед новой попыткой разобраться,
   что произошло и не был ли уже вызван Gemini.
3. Проверить источник, сценарий и фактические утверждения. Дословная цитата
   не доказывает истинность остальных реплик. Затем вручную записать только
   эту пробу в её отдельную очередь:

   ```bash
   python -m news_prototype.live_trial enqueue --folder ПУТЬ_ПРОБЫ
   ```

   Запись идемпотентна; сам `enqueue` не отправляет воркеру задание. Для
   одного шага с общей арендой запустить:

   ```bash
   python -m news_prototype.live_trial step --folder ПУТЬ_ПРОБЫ
   ```

   Если `queue_in_use` или `queued`, попробовать шаг позже. `running` означает,
   что воркер принял работу; повторный `step` только проверит тот же UUID.
   `ready_for_review` — ролик создан на воркере. `worker_not_ready` означает,
   что совместимый воркер не подтверждён. Текущее состояние в MongoDB:

   ```bash
   python -m news_prototype.live_trial status --folder ПУТЬ_ПРОБЫ
   ```

   При `uncertain`, `interrupted`, `failed`, зависшем `submitting` или ином
   неясном состоянии сначала проверить воркер и процессы. Не создавать новую
   пробу для обхода сбоя и не повторять POST вслепую.
4. Только после `ready_for_review`, проверки получателя и осознанного решения
   отправить готовое обычное видео в личку владельца:

   ```bash
   python -m news_prototype.live_trial deliver --folder ПУТЬ_ПРОБЫ
   ```

   При `review_uncertain` или застрявшем `sending_review` сначала проверить
   личный чат и состояние; повторной отправки программа не делает. Видео
   больше 50 МиБ не отправляется через стандартный Bot API и остаётся на
   воркере. Пересылка в группы и публикация в канал не реализованы.

Функция покадровой проверки или ручной коррекции ролика здесь не добавлена.
Сначала нужно проверить качество одной живой пробы и лишь после отдельного
решения переходить к дайджестам или рабочему развёртыванию.
