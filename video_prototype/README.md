# Ручной прототип видеокружков

Это отдельный CLI для проверки цепочки на InstaBox, не публичный сервер.
Рядом подготовлен экспериментальный обработчик бота; сам CLI не использует
LLM, БД, очередь, кэш и панель. Анимация намеренно
заменяема: сейчас это проверенный PNGTuber с двумя положениями рта, реагирующими
на громкость, и двумя фиксированными морганиями. Это не фонемный lipsync.

## Что нужно на InstaBox

- `ffmpeg` с `libx264` и AAC в `PATH`.
- Python-окружение `/data/video-prototype/.venv` с Pillow.
- Для TeraTTS: окружение `/data/teratts-test/.venv` с `numpy`, `onnxruntime`,
  CPU `torch`, `transformers`, `huggingface_hub` и `num2words`, и скачанная
  версия модели в `/data/teratts-test/hf`. Путь к Python меняется через
  `--tera-python`, к кэшу — `--hf-home`. Модель использует собственный код
  (`trust_remote_code=True`) с закреплённым revision; запуск воркера работает
  только с уже скачанной моделью (`local_files_only=True`).
- TeraTTS: `ru_m1`, `duration_scale=1.1`, CPU, seed 42 по умолчанию.
  Текст до 480 символов делится по предложениям (до 200 символов на часть,
  длинное предложение — по словам), части соединяются с паузами 250 мс.
  Сначала включается автоматический RUAccent, затем исправляются проверенные
  формы «Бендер», «укуси», «мешки», «отполировать» и «луна-парк»: для
  произношения последнего ставится ударение на «у» и убирается дефис. Это не гарантирует
  отсутствие ошибок и повторов. Каждый результат проверяется на лимит 60 с.
- [Лицензия модели](https://huggingface.co/TeraSpace/TeraTTSv2): Open RAIL-M
  с дополнительным указанием авторства в коммерческих продуктах; см. также
  применимые ограничения, уведомления и лицензии компонентов в репозитории модели.
  Модель, кэш, изображения и секреты не включаются в Git.
- `/data/video-prototype/preview/closed.png`, `open.png`, `blink.png` —
  согласованные одинаково кадрированные квадратные картинки. Координаты масок
  привязаны к ним: другая композиция потребует обновить маски в `render.py`.
- Для отправки — тот же бот, администратор канала-склада; доступ к целевому чату.
  Токен запрашивается в терминале скрытым вводом или берётся из `BOT_TOKEN`.
  Никуда в чат его отправлять не нужно. Токен даёт доступ ко всему боту.

## Проверка без TTS и без Telegram

Из каталога, в котором находится `video_prototype/`:

```bash
python3 video_prototype/pipeline.py --audio /data/xvibe-test/proba-emotion.wav --no-send
```

Выведется путь к `video.mp4` в новой папке `/data/video-prototype/clips/clip-…`.
Для просмотра её можно временно раздать через знакомый HTTP-сервер. Публичная
раздача открывает файлы в выбранном каталоге. Параметры `--frames-dir`,
`--output-dir`, `--render-python` меняют расположения.

## Весь ручной цикл

```bash
python3 video_prototype/pipeline.py --text 'Ну, чего уставился? Я Бендер. Давай, удиви меня!' --channel-id -1001234567890 --chat-id -1002345678901
```

В примере указаны условные ID; подставьте реальные. После рендера скрипт запросит токен, загрузит MP4 в канал, сохранит Telegram
`file_id` в `result.json` и отправит его в тестовый чат. Если не указывать
`--chat-id`, отправка будет только в канал. Для пробы без Telegram можно
заменить оба ID на `--no-send`. Длинный текст может быть обрезан моделью или
дать видео длительностью 60 секунд и больше; такой ролик здесь отклоняется.
Качество TeraTTS и длительность для каждой новой фразы необходимо проверять:
модель может менять интонацию, пропускать и повторять слова. Подсказки ударений
не гарантируют правильного произношения. `--seed` доступен для ручных проб.

Для ручного теста ответа можно дополнительно указать `--reply-to-message-id ID`;
это ID сообщения **в выбранном чате**. Для темы форума также поддерживается
`--message-thread-id ID`. По умолчанию ручной запуск не отвечает на сообщение.
`--chat-id` выбирается при каждом запуске, в коде нет фиксированного чата.

Будущая интеграция в бота должна брать `message.chat.id` и `message.message_id`
из каждого конкретного запроса, а для тем — соответствующий `message_thread_id`.
Если запрос сделан ответом, контекст исходного сообщения следует передавать по
аналогии с «Экс мнение»: `get_reply_source_text` берёт текст или подпись.
Сам кружок отвечает на сообщение с запросом, как `message.reply` в существующем
обработчике. Живая цепочка проверена пользователем в тестовой группе.

При сбое повторной отправки `result.json` сохраняется после загрузки в канал,
чтобы не потерять `file_id`. Ручные пробы в `clips` на `/data` накапливаются и автоматически не удаляются;
для каталога задач `jobs` действует описанная ниже очистка. Текст, запись голоса и медиа могут быть
чувствительными: этот эксперимент не является безопасным продакшен-сервисом.
При публичном использовании чужого голоса или образа следует проверить права.

Тесты без модели и Telegram:

```bash
python3 -m unittest tests.test_video_prototype -v
```

## Экспериментальный HTTP-воркер

`worker.py` принимает задания для одного экземпляра и возвращает `file_id` из
канала-склада. Это **не продакшен-сервис**; цепочка проверена в тестовой
группе, но условия отказа ещё не проверены. Воркер не принимает `chat_id`: отправку ответа в конкретный чат и тему выполняет будущий
обработчик бота, а не воркер.

Настройки процесса: `BOT_TOKEN`, `STORAGE_CHANNEL_ID`, `VIDEO_WORKER_KEY`
(не менее 24 символов), опционально `--port` (8088), `--bind` (0.0.0.0),
`--output-dir` (`/data/video-prototype/jobs`), `--timeout` (600 секунд) и
`--smoke-plate ПУТЬ` для согласованного дымка. Подложка должна соответствовать
согласованным исходным кадрам, храниться вне каталога задач и оставаться доступной
при перезапуске; если переданный файл отсутствует, служба не запустится. Без
этого флага используется прежний рендер. Огонёк пульсирует, выделенный из
оригинала дым поднимается на статичной бездымной подложке.
Новые библиотеки для HTTP не нужны: используется стандартная библиотека Python.
Все запросы требуют `Authorization: Bearer <VIDEO_WORKER_KEY>`. Внешнее
подключение должно использовать HTTPS-порт платформы; сам воркер — HTTP и
не должен считаться защищённым продакшен-интерфейсом.

- `GET /health` — сервер жив; не проверяет готовность синтеза или Telegram.
- `POST /jobs` — JSON `{"request_id":"<uuid>","text":"…"}`; 202 означает
  задачу, принятую в работу. Результат надо получить отдельно. При повторе с тем
  же UUID и текстом возвращает текущий статус; при другом тексте или занятом
  воркере — 409. Одновременно выполняется одна задача, очередь отсутствует.
- `GET /jobs/<uuid>` — статус `running`, `done` с `file_id` или `failed`.

Повторы и состояния хранятся только в памяти, максимум 100 записей; при
перезапуске они теряются, старые записи удаляются. Поэтому защита от повторной
обработки не переживает перезапуск или вытеснение и не гарантирует exactly-once.
Клиент не должен отправлять новый UUID после неоднозначного сетевого сбоя.
На диск сохраняется `/data/video-prototype/jobs/<uuid>/worker.log` и результат
работы. В этой версии подготовлена очистка: после запуска воркера и затем не
чаще раза в сутки после завершения очередной задачи фоновый поток удаляет только
папки в `--output-dir` с каноническим UUID и обычным файлом `worker.log`, если
папка и журнал не менялись как минимум 30 суток. Удаляются и локальные аудио,
видео, `result.json` и журнал; сообщения в канале-складе не удаляются. Активная
задача защищена блокировкой общего `JobStore`, принятие задачи синхронизировано
с удалением. Символические ссылки и папки нераспознанного вида пропускаются.

Это защита для **одного экземпляра воркера** на каталог задач: не запускайте
другой воркер со старой или новой версией с тем же `--output-dir` параллельно,
и не используйте этот каталог для ручных параллельных тестов. При простое
очистка не будит InstaBox: следующая проверка произойдёт после работы или
рестарта. Отдельные ручные пробы в `/data/video-prototype/clips`, записи,
модели и общий журнал systemd эта очистка не затрагивает. Действующее
развёртывание обновится только после установки нового кода и перезапуска службы.

Запуск создаёт новый процесс TeraTTS для каждого запроса — модель между задачами
не остаётся в памяти.
До продакшена нужны устойчивое хранение задач, корректные перезапуски,
ограничения доступа и нагрузки, политика хранения, тестирование отказов и
интеграция с ботом.

```bash
python3 -m unittest tests.test_video_prototype tests.test_video_worker -v
```

## Экспериментальное подключение бота

`handlers/bender_clip.py` обрабатывает `/bender <вопрос>` и `Экс, кружок <вопрос>`
в группах, где администратор включил «Кружки Бендера» в `/panel`. По умолчанию
функция выключена; в личных чатах этот экспериментальный обработчик не работает.
Пока идёт подготовка, бот случайно выбирает и меняет одно сообщение-статус
каждые 15 секунд, избегая непосредственного повтора.
Если команда отправлена ответом на сообщение, в контекст попадает его текст или
подпись. Сгенерированный кружок будет ответом на команду пользователя в том
же чате и теме. Если команда удалена, Telegram может отправить кружок без привязки
к ней (`allow_sending_without_reply`). Статусы и текстовые ошибки работают так же.
Бот записывает запрос в общую FIFO-очередь MongoDB (до 10 запросов, включая
текущий) и показывает случайный статус в духе Бендера. Один потребитель по
очереди запрашивает ответ LLM, передаёт его воркеру и отправляет полученный
`file_id` в исходный чат и тему. Когда воркер явно ответил, что занят, запрос
остаётся в очереди и повторяется с тем же UUID. Перезапуск бота сохраняет
ожидающие запросы; для активной задачи бот проверяет сохранённый UUID, а не
отправляет её заново. Если ответ от воркера или Telegram неизвестен, бот не
повторяет генерацию или отправку автоматически и сообщает об этом. Возможна
потеря результата при сбое непосредственно перед отправкой или при потере
состояния воркера: гарантия exactly-once здесь невозможна. При заполненной
очереди бот просит попробовать позже. Если Telegram не подтвердил постановку
или отправку, не следует повторять запрос, не проверив чат.

Очередь занимает один документ `bender_video_queue` в MongoDB. Запросы и их
контекст хранятся до завершения, после чего удаляются из очереди; при недоступной
базе новые запросы не могут быть надёжно приняты. Потребитель использует
обновляемую блокировку, при аварийном завершении её срок — до 60 секунд.
Лимит ожидания воркера (660 секунд) начинает отсчитываться только при обработке,
а не при постановке в очередь. Очередь не сохраняет команды, пришедшие, пока бот
не получал обновления Telegram.

На стороне работающего бота нужны `BENDER_WORKER_URL` (корневой HTTPS URL
опубликованного сервиса InstaBox) и `BENDER_WORKER_KEY` (значение
`VIDEO_WORKER_KEY` с InstaBox). URL без пути; токен Telegram бота в обоих
окружениях должен относиться к одному и тому же боту. Сервис должен быть запущен,
доступен снаружи и слушать `0.0.0.0`, а не только localhost. Сам по себе публичный
URL не гарантирует пробуждение вручную остановленного InstaBox. Пользователь
проверил автопробуждение после простоя и доставку после полной перезагрузки.
Устойчивость при сбоях полностью не проверена. Кэш file_id, устойчивый к
перезапускам учёт задач и отдельный вызов API wake не реализованы. Длинный ответ LLM может быть сокращён до лимита 480 символов.

Тесты очереди используют симулятор MongoDB из `requirements-test.txt`; без него
эти тесты пропускаются. Они не заменяют проверку на настоящих Render и InstaBox.

```bash
python3 -m unittest tests.test_bender_queue tests.test_bender_clip tests.test_bender_worker_client -v
```

## Проверенное развёртывание

На InstaBox под службой systemd `bender-video.service` работает код
`/data/video-prototype/code-smoke-828b78d`. Drop-in `smoke.conf` включает
`--smoke-plate /data/video-prototype/assets/smoke-free-103.png`; пользователь
подтвердил работу обычного кружка. Базовый unit и предыдущая копия
`code-speech-128a140` сохранены для отката. Перезагрузка после этого обновления
отдельно не проверена; ранее пользователь проверил кружок после перезагрузки
и самостоятельное пробуждение машины после простоя.
При переносе нового кода не запускать два воркера одновременно на одном каталоге
задач; после замены пути службы проверить `is-active`, порт и реальный кружок.
Не удалять рабочую копию до проверки новой. Секреты в чат не присылать.

## Подготовленное подключение случайной сцены

В этом коде worker может использовать одобренные случайные сцены и более живой
рот, но только при явном запуске с `--random-guests --portrait ПУТЬ` и существующей
`--smoke-plate`. Без этих новых аргументов рендер остаётся прежним. Портрет сенсея
нужен как постоянный читаемый файл вне очищаемого каталога задач; воркер откажется
запускаться, если файл или подложка отсутствуют. Не менять конфигурацию рабочей
службы без отдельного согласования и проверки свободной очереди.

Seed сцены — UUID задачи, отдельно от seed озвучки. В папке нового ролика рядом с
`video.mp4` сохраняется `scene.json` с выбранными гостями, эффектами и взглядами.
В каждом ролике присутствует хотя бы один из трёх персонажей, а пузырьки,
пирамида и монета выбираются независимо. Взгляды не анализируют текст и не
гарантированы на каждого персонажа; табличка пока не реализована. Передача на
склад и запасная однократная доставка в чат используют существующий pipeline.

## Изолированное сравнение бесплатных голосов на InstaBox

`tts_audition.py` не подключён к рабочему воркеру и не переключает TTS. Он
синтезирует одинаковый текст, последовательно отправляя в указанный чат аудиофайлы
и время генерации. Два варианта Edge — один голос Dmitry с обычной и пониженной
высотой, не два разных диктора. Edge — неофициальный сервис, работоспособность и
условия использования не гарантированы. `--gemini` дополнительно проверяет голоса
Charon и Fenrir через API Gemini; они могут оказаться недоступными для проекта или
региона. Пробу следует запускать только с ключом Free Tier без billing;
ключ вводится скрыто или читается из закрытого файла. Скрипт не может автоматически проверить тариф ключа: если проект
платный, Google может выставить счёт. Данные Free Tier могут использоваться Google
для улучшения продуктов. Запросы и аудио передаются провайдерам с InstaBox.

Нужен отдельный venv с `edge-tts`, `BOT_TOKEN` в окружении или скрытый ввод токена.
Например, из каталога с `video_prototype`:

```bash
/data/video-prototype/tts-audition-venv/bin/python -m video_prototype.tts_audition --chat-id ВАШ_CHAT_ID
# Дополнительно Gemini (используйте только Free Tier без billing):
/data/video-prototype/tts-audition-venv/bin/python -m video_prototype.tts_audition --chat-id ВАШ_CHAT_ID --gemini
```

Для темы форума можно добавить `--thread-id`. Аудиофайлы и текст сохраняются в
новой папке `clips/tts-audition-*`, автоматически не удаляются. Не использовать
секретные тексты. Если Telegram не подтвердил отправку, скрипт останавливается;
перед повтором обязательно проверить чат, чтобы не отправить дубликаты. Проба не
проверяет качество автоматически и не гарантирует скорость в боевом режиме.

Для длинной пробы Edge без подключения к воркеру есть отдельный модуль
`video_prototype.edge_long_trial --chat-id ВАШ_CHAT_ID` (нужны `BOT_TOKEN`,
`edge-tts` и ffmpeg). Он разбивает тестовую фразу на части по 65 символов,
повторяет неудачную часть один раз, декодирует и соединяет их с паузами 150 мс.
Только после успешного сбора он отправляет обычный голос и локально пониженный.
Если Telegram не подтвердит отправку, перед повтором обязательно проверить чат;
часть сообщений могла уже прийти. Ручные пробы сохраняются в `clips` и не
удаляются автоматически. Разбиение может портить интонации и не доказывает
надёжность Edge для production.

Для ручных проб Gemini можно передать `--gemini-key-file ПУТЬ`: файл должен
принадлежать текущему пользователю и не давать доступ группе и остальным
(например, 0600), символьные ссылки запрещены. Ключ не выводится в журнал и не
передаётся в аргументах процесса. Это только для ручной пробы, к рабочему воркеру
не подключено. Скрипт не проверяет биллинг: необходимо самостоятельно убедиться,
что проект остаётся бесплатным и billing не включён. Не добавляйте файл ключа в Git.

Для выбора готовых голосов без повторной отправки Charon/Fenrir используйте,
например, `--gemini --skip-edge --voices Orus Algenib Iapetus`. Это отдельные
ручные запросы, расходующие квоту; результат и скорость заранее не гарантированы.
