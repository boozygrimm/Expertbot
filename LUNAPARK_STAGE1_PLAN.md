# План первого этапа Mini App «Луна-парк»

**Дата:** 2026-11-21. **Статус:** план, к исполнению не принят. Кода в этой правке
нет. Все четыре открытых вопроса стратегии закрыты владельцем — план опирается
только на них и на проверенный код.

## 1. Зафиксированные решения

| Вопрос | Решение | Что из этого следует |
|---|---|---|
| Доступ | по существующим игрокам в базе | без запросов к Telegram, быстрый вход |
| Хостинг | один origin, всё в процессе бота | CORS не нужен, `connect-src 'self'` |
| Тестовый контур | тот же бот за флагом | новая коллекция, доступ по списку ID |
| Наследие и достижения | решаем позже | в план первого этапа не входят |

Плюс ранее принятое: прогресс обнуляется, старая база — архив, пишет только Mini
App, счётчики считаются формулой, рейды отложены, старые команды гасятся с
заглушкой, в чат — только по кнопке «Поделиться».

## 2. Первое следствие: раздел «доступ» упрощается

`handlers/auth.py:12–38` пропускает **все личные сообщения** без проверки, а
группы ограничивает через `auth_chats`. Так как вход в мини-апп идёт из лички и
решение — «по существующим игрокам», проверка становится такой:

1. `initData` уже проверен (`miniapp_backend/auth.py`), из него берём user ID;
2. ищем документ в `alchemy_players` по этому ID;
3. если документа нет — отказ с понятным текстом («сначала зайди в игру через
   бота»), а не пустой экран.

Telegram-запросов на входе нет вообще. Это и быстро, и не тратит лимиты.

**Ограничение, которое надо знать:** игрок, который никогда не заходил в бота,
в мини-апп не попадёт. По решению владельца это приемлемо — старая игра ещё
работает на первом этапе, значит путь «зайти в бота, потом в мини-апп» открыт.

## 3. Второе следствие: `miniapp_backend/telegram_stand.py` почти не нужен

Этот стенд специально раздаёт статику и проверяет `connect-src 'self'`, то есть
рассчитан ровно на один origin. При решении «один origin» его CSP-часть и
раздача файлов подходят как есть; выдумывать раздельные домены и CORS не нужно.

## 4. Что именно создаётся

### 4.1 Новая коллекция

Название — `lunapark_players` (новое, старое `alchemy_players` не трогаем; оно
остаётся архивом).

Поля (все — по одному писателю, серверу мини-аппа):

| Поле | Смысл |
|---|---|
| `user_id` | проверенный Telegram ID, уникальный индекс |
| `version` | для условной записи (сравнение и увеличение) |
| `collection` | открытые элементы лаборатории |
| `discovered` | открытые пары/рецепты |
| `mastery` | лабораторное мастерство |
| `project` | текущий проект парка и его прогресс |
| `last_craft_at` | момент последнего крафта для формулы/лимитов |
| `updated_at` | служебное |

Уникальный индекс по `user_id` — обязателен: он не даёт создать два профиля
одному игроку даже при гонке.

### 4.2 API (в процессе бота, тот же origin)

| Роут | Что делает |
|---|---|
| `POST /api/session` | обмен `initData` на короткий токен сессии |
| `DELETE /api/session` | выход |
| `GET /api/profile` | склад, открытые элементы, мастерство, проект |
| `POST /api/craft` | один крафт: два ингредиента, ключ идемпотентности |
| `POST /api/share` | подготовка текста «Поделиться» (без отправки) |

Все четыре уже имеют основу: `miniapp_backend/app.py` содержит `security_headers`,
`/api/session` и `/api/alchemy/me`; `sessions.py` — сессии в памяти.

Что меняется: `/api/alchemy/me` смотрит в новый источник, а `/api/craft` пишет
**только** в `lunapark_players`.

### 4.3 Счётчики формулой

Не хранить «накопленное». Хранить момент действия и считать при чтении — как
уже сделано для похода в `alc_core.py:1058–1064`:

- `last_craft_at` → сколько крафтов доступно сейчас;
- любые будущие таймеры (производство, если вернём) считаются так же;
- запись происходит только в момент действия игрока.

### 4.4 Флаг и тестовый контур

В боте флаги уже есть двух видов: env (`NEWS_*` в `app_setup.py`) и по чату
(`FEATURES` в `handlers/admin_panel.py:206–212`). Для мини-аппа нужен третий,
простой: `LUNAPARK_ENABLED` в окружении + список `LUNAPARK_TEST_IDS`.

- `LUNAPARK_ENABLED` выключен → страницы и API отвечают «ещё не открыто»;
- включён → вход только ID из `LUNAPARK_TEST_IDS`, остальные получают отказ.

Так первая версия живёт на том же боте, но видна только владельцу и 2–3
тестировщикам, и это видно в одном месте, а не размазано по коду.

## 5. Порядок работ по файлам

1. `miniapp_backend/store.py` (новый) — доступ к `lunapark_players`: создание
   профиля, условная запись по `version`, чтение.
2. `miniapp_backend/craft.py` (новый) — расчёт одного крафта поверх уже
   существующего `crafting.py`; пишет только через `store.py`.
3. `miniapp_backend/app.py` — добавить `/api/profile`, `/api/craft`, `/api/share`;
   проверка `LUNAPARK_ENABLED` и списка ID.
4. `app_setup.py` — смонтировать раздел `/miniapp/` в существующий `aiohttp`
   (рядом с `handle_healthcheck`), без второго процесса и без второго планировщика.
5. `miniapp_preview/` — переключить `offline_adapter.js` на API, оставив офлайн
   режим как демо.
6. Заглушки на старые команды алхимии — **после** того, как работает пункт 4.
7. Выключение семи задач планировщика — **после** пункта 6.

Пункты 1–5 не трогают ни одной строки `handlers/alc_*.py`. Это главное свойство
плана: старая игра продолжает работать, пока новая не доказала, что работает.

## 6. Проверки на этом этапе

- два параллельных крафта одного игрока не дают двойного списания (ключ
  идемпотентности + версия документа);
- повтор запроса с тем же ключом возвращает тот же результат;
- вход с чужим/просроченным `initData` → отказ;
- вход ID не из списка → отказ с понятным текстом;
- профиль сохраняется между устройствами;
- ни одна команда бота не изменила поведение (прогон существующих тестов).

## 7. Чего в этом плане нет и почему

- **Рейдов, форта, наследия, достижений** — отложены владельцем.
- **Слоя атомарной записи поверх `alchemy_players`** — не нужен: бот перестаёт
  писать в новую коллекцию, у неё один писатель.
- **Раздельных доменов и CORS** — не нужны при одном origin.
- **Отдельного тестового бота** — решение: тот же бот за флагом.
- **Фоновых задач для новой лаборатории** — не нужны: счётчики формулой.
