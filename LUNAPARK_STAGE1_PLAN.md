## 1. Что из этого меняет план

**Слой записи писать не нужно — нужно снять с него ограничения.** В
`isolated_store.py` уже есть всё, что требовалось в варианте 2 стратегии:

- условная запись по `_alc_rev` (`condition` сравнивает ревизию);
- журнал `_alc_ops` в том же документе, обновление одним `update_one`;
- повтор с тем же `operation_id` возвращает сохранённый результат, а не
  выполняет второй раз;
- тот же ключ с другой командой → `OperationKeyConflict`;
- обрыв записи → `OutcomeUnknown`, повтор только с тем же ключом;
- `WriteConcern(w='majority')` и `ReadConcern('majority')`.

Два ограничения, которые надо заменить — сознательно, а не «починить на глаз»:

1. **`isolated_test_only=True` и имя базы `lunapark_test_*`.** Ограничение
   защитное: оно не даёт случайно направить сторадж на рабочие данные. Для
   настоящей коллекции нужно явное разрешение (например, параметр
   `allow_production=True` плюс проверка, что коллекция — `lunapark_players`),
   а не просто снятие проверки.
2. **`MAX_OPERATIONS = 256` без вытеснения.** После 256 операций запись
   блокируется (`OperationLogFull`). Для 10–30 игроков это ~10 крафтов на
   человека — мало. Нужна политика: либо отдельная коллекция журнала, либо
   сжатие журнала по времени при сохранении идемпотентности в пределах окна
   повторов.

**`ALLOWED_FIELDS`** сейчас — `inventory`, `discovered`, `last_craft`,
`production_slots`. Для лаборатории этого достаточно; новые поля (мастерство,
проект) добавляются явно.

## 3. Порядок работ

1. **Политика журнала + снятие test-only ограничения** в `isolated_store.py`,
   с тестами: 300 операций подряд, повтор после заполнения, два одновременных
   крафта, обрыв записи.
2. **Коллекция `lunapark_players`**: уникальный индекс `user_id`, обёртка,
   создание профиля при первом входе.
3. **Роут `POST /api/craft`** поверх `IsolatedProfileStore.craft` (он уже
   готов и покрыт тестами).
4. **Роут `POST /api/share`** — текст для кнопки «Поделиться», без отправки.
5. **Флаг и монтирование**: `LUNAPARK_ENABLED`, `LUNAPARK_TEST_IDS`,
   `/miniapp/` в существующем `aiohttp`.
6. **Интерфейс**: `miniapp_preview/` на API, офлайн-режим остаётся демо.
7. **Заглушки** на старые команды алхимии — после шага 6.
8. **Выключение семи задач планировщика** — строго после шага 7.

Шаги 1–6 не трогают ни одной строки `handlers/alc_*.py`.

## 4. Проверки

Уже есть и остаются зелёными: 58 тестов мини-аппа. Добавляются:

- 300 последовательных крафтов без `OperationLogFull` (или явный отказ с

- повтор запроса с тем же `operation_id` даёт тот же результат;

- профиль сохраняется между устройствами;
- существующие тесты бота зелёные.

## 5. Открытый вопрос (один)

**Политика журнала операций.** Два варианта, у каждого последствие:

- **Отдельная коллекция журнала** с TTL (например 24 часа): идемпотентность
  держится сутки, документ игрока не растёт. Нужен второй документ и
  согласованность двух записей.
- **Журнал в документе с окном** (последние N операций): просто, одна запись,
  но повтор старше окна будет выполнен заново.

Для 10–30 игроков оба варианта достаточны; выбор влияет на гарантии. Рекомендация
— окно в документе (проще, одна атомарная запись), с явным отказом «повтор
слишком старый», а не молчаливым повтором.
